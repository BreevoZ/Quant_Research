## English quick start

Replay historical queues and track hypothetical orders without altering the real book. Tests cover queue invariants and a hand-written Flow integration fixture.

Commands below run from the repository root, using conda `mx` for Python:

```bash
cmake -S ashare/vorder_sim -B ashare/vorder_sim/build
cmake --build ashare/vorder_sim/build -j4
ctest --test-dir ashare/vorder_sim/build --output-on-failure
```

See the [A-share guide](../README.md) for data contracts, paths and research limitations.

`cd ashare/vorder_sim` unless they explicitly start from the repository root.

## 中文技术说明

下文保留原项目技术细节；项目内相对命令以 `ashare/vorder_sim` 为工作目录，仓库根命令另行标明。

基于原始 TL 逐笔数据,在真实盘口演化中插入策略(虚拟)订单,精确追踪它们的
**排队位置**和**成交**,全程**不影响真实盘口**。

## 架构(datacheck 主干 + auction uncross + 影子记账层)

```
TL / Flow 逐笔 ─parse─► UnifiedRecord ─► LobBuilder(真实簿, 原样, 逐字节复现)
                             │                    │ 每事件(只读回调)
                             │                    ▼
                             │            SweepAllocator(影子记账层, 每股票一个)
                             └─预扫─► 主动单预算 Q ──► 按(价格优先→插入先后)分配成交
                                                        │
                                                        ▼
                                            VirtualOrderTracker × N(B档L3排队 + 竞价uncross)
```

- **真实盘口**:直接复用 `datacheck_final` 的 `LobBuilder`(`lob_builder.{h,cpp}` 拷贝)。
  虚拟单**绝不进真实簿**;整层通过只读回调 `setEventHook` 旁挂。
  已验证:挂上追踪器后真实簿 order 表与 datacheck 输出**逐字节一致(md5 相同)**。

  > ⚠️ **这是拷贝不是共享库,`datacheck_final` 那份才是基准。**
  > 本项目在其上**只做了纯附加扩展、未改任何重建语义**:`setEventHook()`(只读事件回调)、
  > `setLiteMode()`(跳过 `orderTable_`/`tradeTable_` 构造,vsim 不用这两张表)、
  > `bestBid()`/`bestAsk()`(聚合盘口只读访问器,供 uncross 与最优价查询),共 +112 行。
  > **`datacheck_final` 若再修重建规则,必须手动同步过来**——否则本项目回放出的"真实历史盘口"
  > 会与验证工具产生分歧,而上面那条逐字节一致的保证正是本项目全部结论的地基。
  > 同一份规则还有第三处实现:`auction/cpp/auction_lob_builder.cpp`。
- **影子记账层**:`sweep_allocator.h` + `sweep_budget.h`。同一股票的多笔虚拟单从
  **同一个主动单预算**里取量 → 同价串行、异价耦合、不再凭空超发(见「多虚拟单」一节)。
- **集合竞价撮合**:`uncross.h` 移植自 auction 项目 `computeAuctionSnapshot`
  (最大成交量→失衡最小→价高)。
- **单腿排队**:`virtual_order_tracker.h`,B档精确 L3 队列。

## 排队模型(B档)

只为虚拟单价位 P 维护"我侧" L3 FIFO 队列 + `aheadQty`(前方剩余量):
- **t0 插入**:排在 P 档现存全部真实单之后,`aheadQty` = P档我侧现存总量。
- **成交(zb)到 P**:`aheadQty>0` 先扣前方;扣光后(到队首)后续成交量按**无冲击假设**归我。
- **撤单(cl)到 P**:按订单号定位——在我前(`seqNo<insertSeq`)则 `aheadQty` 减、我前移;在我后则忽略。
  (这就是 B 档相对 L2 的核心增益:原始数据每笔撤单点名订单号,精确定位前/后。)
- **委托(wt)到 P**(t0后):排我后面,不影响 `aheadQty`。

## 集合竞价

- 竞价段累积队列,不按连续成交撮合。
- 竞价终点(09:25:00 / 15:00:00)对含虚拟单的簿做 uncross,得清算价 `p*`:
  - 限价严格优于 `p*` → 全成(成交价 = `p*`)。
  - 限价 = `p*`(边际) → 按 `maxVol - 更优量 - aheadQty` 部分成交。
  - 撮不掉的残量 → 继续挂,转连续段追踪。

## 用法(批量输入文件)

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j

# 数据源二选一:
./build/vsim --tl-dir /path/to/tl_dir  --date YYYYMMDD --orders orders.csv [--out results.csv] [--no-bounds]
./build/vsim --flow   /path/to/flow.csv --date YYYYMMDD --orders orders.csv [--out results.csv]

# 三种输出可任意组合(见「输出」一节): 逐腿明细CSV / 组合汇总报告 / 逐笔成交事件CSV
./build/vsim --flow flow.csv --date 20260707 --orders orders.csv \
    --out results.csv --report report.txt --fills fills.csv
./build/vsim --flow flow.csv --date 20260707 --orders orders.csv --report -   # 报告直接打到 stdout

# 加速: 解析结果缓存(同日重复跑免重扫大文件) + 线程数
./build/vsim --tl-dir DIR --date 20260707 --orders orders.csv --cache-dir /path/to/cache --workers 60

# 预缓存: 扫源一次把全市场(或指定股票)解析结果全部落盘, 之后任意订单查询秒回
./build/vsim --precache --tl-dir DIR --date 20260707 --cache-dir /path/to/cache            # 全市场
./build/vsim --precache --tl-dir DIR --date 20260707 --cache-dir /path/to/cache --symbols 600000,000001
```

- **`--tl-dir DIR`**:解压后的 TL 目录(含 `mdl_4_24_0.csv` 或 `mdl_6_33_0.csv`+`mdl_6_36_0.csv`)。
- **`--flow flow.csv`**:单个 Flow 统一格式 CSV(tltoflow 产物,一个文件含全市场)。
  两种源建出的 LOB 逐字节一致 → **同一批订单在 TL / Flow 上结果相同**(已实测)。
- **`--out FILE`**:逐腿明细 CSV(每笔虚拟单一行,21 列;见「输出」一节)。
- **`--report FILE`**:组合级纸面汇总报告(总览 / 终态 / 按方向 / 按市场 / 按股票 / 成交进度)。
  `FILE=-` 直接打到 stdout。给人扫一眼判断整篮子表现用。
- **`--fills FILE`**:逐笔成交事件 CSV(每笔单**每次成交一行**:时间/量/价/来源/累计/剩余),
  追踪每笔单如何一步步成交到全成。
- `--no-bounds`:只算中性成交量,不算同毫秒乐观/悲观上下界 → 省 2/3 追踪开销(不需要区间时用)。
- **`--cache-dir DIR`**:解析结果缓存目录。首跑把每只股票已解析的 `UnifiedRecord` 存成定长二进制
  (`DIR/<date>/<tl|flow>_<market>_<symbol>.bin`);同日再跑直接读缓存、免重扫多 GB 的 TL/Flow 大文件。
  按 `(date, 源类型, market, symbol)` 分文件,换日/换源自动隔离;缓存缺失的股票才回源解析并补写。
  **失效检测**:缓存头带**源文件指纹**(各源文件的 size+mtime)和**解析器版本号**;源被重生成
  (如重跑 tltoflow)或解析器逻辑升级(版本号 +1)→ 命中的旧缓存自动作废、回源重解析,不会喂出过期数据。
- **`--precache`**:预缓存模式。扫源**一次**,把全市场(或 `--symbols` 指定)股票的解析结果全部落盘,
  不跑订单(不需要 `--orders`)。之后对该日任意股票的订单查询都直接命中缓存(亚秒级,见下方性能实测)。
- **`--symbols 600000,000001`**:配 `--precache`,只预缓存指定代码(按代码首位或 `.SH/.SZ` 后缀分市场);缺省=全市场。
- **`--workers N`**(默认 60):并行度。用于**分块并行解析**(单文件多线程各扫一段)和**多股并行建簿+追踪**
  (每只股票独立算、写各自结果,互不冲突)。

`--tl-dir` 是解压后的 TL 目录(含 `mdl_4_24_0.csv` 或 `mdl_6_33_0.csv`+`mdl_6_36_0.csv`)。

### 性能实测(20260707 真实数据)

环境:internresearch01,72 核 / 251GB 内存,`--workers 60`(默认);源文件已在 OS 页缓存
(= 日常反复使用场景;当日**首次**从磁盘读会额外受 I/O 限制)。订单集:25 腿 × 4 股
(600000 / 688981 / 000001 / 300750,覆盖被动/marketable/竞价/撤改单)。

| 场景 | 源 | 耗时(wall) |
|---|---|---|
| 冷解析:TL 目录(19+14+14 GB 三文件) | TL | **16.7s** |
| 冷解析:全市场 flow.csv(55 GB) | Flow | **13.7s** |
| 冷解析:4 股子集 flow(157 MB) | Flow | 3.4s |
| **热缓存**:同 25 腿 4 股,三口径 | 缓存 | **3.2s** |
| 热缓存 + `--no-bounds`(只算中性) | 缓存 | 2.6s |
| 热缓存:**200 腿** 4 股,三口径 | 缓存 | 11.6s |
| 热缓存:**单腿单股**(000001) | 缓存 | **0.4s** |

**全市场 `--precache`**(全量解析所有标的并落盘,与上面"只解析目标股票"的冷解析不同):

| 场景 | 标的数 | 缓存体积 | 耗时(wall) |
|---|---|---|---|
| Flow 55GB 全市场 precache | 5194 只 | 44 GB | **5m14s** |
| TL 47GB 全市场 precache | 7501 只(含债券/基金等) | 56 GB | **11m38s** |
| precache 后任意股票查询(600519 单腿) | — | 命中 | **0.38s** |

- 冷解析扫 55GB 全市场文件 ≈ 14s:60 线程分块并行,CPU 累计 ~6 分钟(≈27× 并行效率)。
  这么快的关键是**前缀拒绝**——每行先只看 instrumentID 是否目标股票,~99.7% 的行读十几个
  字节就丢弃,真正完整解析的只有 ~0.3%;所以它是"扫描 55GB + 解析 160MB"。
  而全市场 precache 是真·全量解析(每行都切分+转数字+写缓存),5m14s 才是解析 55GB 的成本。
- TL 全市场比 Flow 慢(11m38s vs 5m14s):TL 要合并委托/成交两个文件并按序重排,
  且标的数多 44%;两者 CPU 累计相近(~26 分钟),差在并行效率(合并/落盘阶段串行占比高)。
- 缓存命中后与源文件大小无关:每股定长二进制 ~11–57 MB(4 股共 126 MB),
  耗时主要在 LOB 重放 + 追踪,单股单腿 0.4s 起。
- 腿数扩展近线性但摊薄明显:25→200 腿(×8)耗时 3.2s→11.6s(×3.6)——
  同股的腿共享同一次建簿,只有追踪/分配层随腿数增长。
- `--no-bounds` 省的是三份追踪器中的两份(3.2s→2.6s);建簿重放占大头,故不到 1/3。

`orders.csv` 每行一个订单生命周期动作,用 `id` 串联(可带表头,自动跳过)。**字段用数字编码**
(字段两侧空格自动去除):

| 字段 | 数字编码 | 兼容的旧字符串 |
|---|---|---|
| `action` | `1`=place `2`=cancel `3`=modify | `place`/`cancel`/`modify` |
| `market` | `101`=上海 `102`=深圳 | `sh`/`sz` |
| `side`   | `1`=买 `2`=卖 | `buy`/`sell`(或 `b`/`s`) |
| `t`      | 距零点毫秒数,整数(`1`=1 毫秒,如 `34210500`) | `HH:MM:SS[.mmm]`(如 `09:30:10.500`) |

`id`/`symbol`/`price`/`qty` 保持原样(`symbol` 有前导零故仍为串)。数字与旧字符串写法**可混用、结果逐字节一致**。

```
id,action,market,symbol,side,price,qty,t
o1,1,101,600000,2,8.93,300000,34210000    # place 卖 600000 @8.93, 09:30:10
o1,2,,,,,,34260000                          # cancel(仅需 id+t): 09:31 撤 o1(余量撤销, 已成交保留)
o2,1,101,600000,1,8.85,100000,34500000     # place 买 @8.85, 09:35:00
o2,3,,,,,8.88,100000,37800000              # modify 改价到 8.88(10:30, 继承 market/symbol/side; 新腿 o2#2)
o3,1,102,300750,1,384.00,5000,36000000     # place 买 300750 @384, 10:00:00
```

- **action**:`1`=place(下单)/`2`=cancel(撤单, 仅需 id+t)/`3`=modify(改单, id + 新 price/qty + t;
  market/symbol/side 继承原单)。**兼容旧格式** `id,market,symbol,side,price,qty,t0`(无 action 列 → 视为 place)。
- **modify = A股 cancel-replace**:t 时刻撤旧单 + 按新价量重挂,**丢失排队优先级**(新单排队尾),
  输出里新腿 id 记作 `<id>#2/#3…`(每次改单一条腿, 便于分别看各腿成交)。
- **多笔共享主动单预算**(见下节):同一股票的多笔虚拟单**会相互影响**(同价串行 / 异价耦合),
  不再各自认领同一批流动性。真实盘口仍然全程只读、逐字节不变。
- **效率**:同一股票多笔共享一次解析+建簿;按市场各扫一次数据(不重复扫大文件)。

## 输出

跑完先在 **stdout** 打一张精简表(每笔的 filled / 区间 / 状态)。另有三路可选文件输出,粗到细:

**1. `--out` 逐腿明细 CSV**(每笔虚拟单一行,21 列):
`id, market, symbol, side, price, qty, t0, arrival_mid, filled, filled_pess, filled_opt,`
`fill_pct, avg_price, through_filled, slippage, state, ahead_remaining, displaced,`
`n_fills, first_fill_t, last_fill_t`。
即中性成交量 / 同毫秒 [pess,opt] 区间 / 成交均价 / 扫价穿透量 / 相对到达中价滑点 / 终态 /
前方剩余量 / `displaced`(位移计,按股票汇总)/ **成交笔数与首尾成交时刻**。

**2. `--report` 组合级纸面报告**(给人读)。六段:
- **组合总览**:委托/成交量 + 填单率、[悲观,乐观] 区间、委托/成交名义、穿透占比、
  市场冲击(位移,按股去重)、零冲击腿数、成交加权滑点。
- **终态分布**:FILLED / PARTIAL / RESTING / CANCELLED 计数。
- **按方向 / 按市场**:买卖、沪深分组的填单率 / 穿透 / 加权滑点(位移是股票级共享量,不在此二表拆分)。
- **按股票**:每股填单率 + 位移(此层位移良好定义)。
- **成交进度**:每笔单一行,`首笔成交→末笔成交` 时刻 + 成交笔数 + 终态,全成标 ✓。

**3. `--fills` 逐笔成交事件 CSV**(最细,做执行/冲击分析的原料):
`id, market, symbol, side, limit_price, order_qty, seq, fill_time, fill_qty, fill_price,`
`venue, cum_filled, remaining`。每笔单每次成交一行,`remaining` 归零即全成的那一刻。
`venue` 区分成交来源:`cont`(连续段被动)/ `auction`(集合竞价 uncross)/ `aggress`(到达即穿价的主动成交)。

## 多虚拟单:共享主动单预算(核心)

**问题**:若每笔虚拟单都"假设只有我一个",同一批流动性会被多条腿各自认领 → **凭空超发**。
实测 600000:8.85 与 8.84 各挂 1000 万股,独立评估会报**两腿各全成(合计 2000 万股)**——
而当日 ≤8.85 的卖方主动流量**总共只有 1865 万股**,物理上不可能。

**做法**:每笔主动单有一个预算 `Q` = 它的**原始委托数量**。同一股票的所有虚拟腿从**同一个 Q** 里
按 **(价格优先 → 插入先后)** 依次取量,取完为止。一个机制同时解决两件事:

| 场景 | 结果 |
|---|---|
| **同价串行**(A、B 都挂买一;前方 50 真实;主动卖 200) | 真实 50 → **A 吃满** → **B 只吃到剩下的** |
| **异价耦合**(A 挂买一、B 挂买二;主动卖单逐档往下扫) | A 吃掉的量**减少了流到买二的量** → B 少成交 |
| **零冲击**(主动单有残量没成交 = slack) | 你吃的是这份 slack → **没从任何真实单嘴里抢** |

实测:8.84 单独挂 1000 万股 → 全成;加上 8.85 的兄弟腿后 → **只成交 576 万(被抢走 424 万股)**。
两腿合计 1576 万股 < 当日该价区流量 1865 万股 ✓ 守恒。

**Q 怎么取**(预扫一遍, 两市场统一, 见 `sweep_budget.h`):
```
Q(X) = 有委托记录 ? (委托量 + 该单在其委托记录之前已成交的量) : (该单总成交量)
```
- **SZ**:委托记录在成交之前、且带完整原始量 → `Q = 委托量`(实测 100% 覆盖)。
- **SH**:立即全成的主动单**根本没有委托记录**(实测占 41.2%)→ `Q = 总成交量`;
  有委托记录的,委托量只记**挂住量**(先吃部分已被净掉)→ 加回先吃量才是原始量。

**`displaced` 列(位移计)**:你从**真实单**嘴里挤走的量(按股票汇总)。两条来源:
- **被动成交**:主动单预算被吃到**负**的那部分(你抢了本该流给更深/更后真实单的量)。
- **marketable 成交**:**全额计入** —— 你到达时吃的是对手盘上真实挂着的量,那些量在现实里
  是被别人吃掉的。**marketable 绝不可能"零冲击"**。

读法:`= 0` → 零冲击(你吃的全是主动单没消化掉的残量 slack);越大 → 无冲击假设被违反得越厉害,
**数字越不可信**。实测:被动挂单在流动性好的票上位移几乎等于成交量(每一股都挤占了真实单),
而在主动单常留残量的场景下可以为 0(见测试 M3)。

**同时刻多笔 marketable 共享可见对手深度**:两笔同时跨价的单不会各自把同一批深度**再吃一遍**;
后扫的那笔只吃得到前一笔剩下的(实测:两笔各 300 万同时跨价,后者成交均价从 10.5728 劣化到 10.6911)。

> ⚠️ **真实盘口不受任何影响**。虚拟单绝不进簿;`LobBuilder` 照常回放磁带、逐字节复现历史簿
> (datacheck / 3秒降频 / 因子链路完全不受影响)。预算分配只发生在**只读的影子记账层**。
>
> 仍然做不到的:被你挤掉成交的真实单,现实中会改挂/撤单、别的参与者会反应 —— 本模型不管。
> 这是无冲击假设不可消除的部分,`displaced` 就是用来量化"你离这个假设有多远"。

## 同毫秒上下界(乐观/悲观)

同一毫秒内"撤前方单 vs 成交"的先后,数据无法确定,却会影响成交量。每笔订单同时跑三个口径:
- **NEUTRAL**:按数据自然(seqNo)顺序 → 单点估计(`filled`)。
- **OPTIMISTIC(上界)**:同毫秒内先撤后成交(前方让路)→ 成交最多(`filled_opt`)。
- **PESSIMISTIC(下界)**:同毫秒内先成交后撤(前方先被吃)→ 成交最少(`filled_pess`)。

真实成交必落在 `[filled_pess, filled_opt]`。区间为 0 宽 = 结果对同毫秒顺序稳健(全成/不成的订单天然如此);
区间宽 = 该订单卡在队首边缘、对顺序敏感,单点数字别太当真。

同毫秒的重排在 **`SweepAllocator` 层**做(不是每条腿各排各的)→ 全篮子共用**同一个**重排。
因此各腿的 `[pess, opt]` 是**自洽的、可相加**的(同一毫秒的真实顺序对全簿只有一种,
各腿分别取最坏排序再相加是不成立的)。

## 到达即可成交(marketable)

若限价穿越对手最优(买 P≥卖一 / 卖 P≤买一),到达时按**对手价位从触及价往外扫单**成交
(成交价 = 对手价, 非我限价 → 滑点真实反映穿价成本), 残量在 P 挂着继续被动追踪。
成交只被**对手方主动**填充(我买单←卖方主动;我卖单←买方主动),排除同向主动在我价位附近的成交。

## 扫价穿透(已实现)

买单 P:凡**卖方成交价 ≤ P** 都算命中你(不只是 ==P);卖单 P 对称(买方成交价 ≥ P)。
一笔卖单吃穿你这一档、继续在更低价成交时,按价格优先本应先打到你——`price==P` 那版会
系统性**低估**成交。实测:被动单被趋势行情"碾过"时,**78%~98% 的成交来自扫价穿透**,漏掉是灾难性低估。
输出里 `其中扫价穿透成交` 列出该贡献。

两层不可互相替代,理由见下面「端到端人工核对」一节。

`vsim_test.cpp` 五层:
1. **32 个手工场景**(已知预期,逐个断言):队首成交、前方消耗、撤前方/后方、扫价穿透(买/卖)+护栏、
   边界(恰好吃完/溢出/跨多前方单/部分撤)、集合竞价(严格优全成/超额封顶/边际不成/劣于清算/
   竞价+连续补成)、收盘竞价 finalize、marketable 到达扫多档 + 主动方向门、同毫秒上下界、
   策略主动撤单、微单等。
2. **4 个多虚拟单场景**(共享主动单预算):**异价耦合**(A 吃满买一 → B 在买二吃不到)、
   **同价串行**(A 吃满 → B 只吃到剩下的)、**零位移**(吃的是主动单残量 slack → 不挤占真实单)、
   **同时刻 marketable 共享对手深度**(B 只吃到 A 剩下的)。四例同时断言各腿 `filled` 和 `displaced`。
3. **500 例单腿 fuzz**(检查必然不变量):`0≤filled≤qty`、`through≤filled`、
   `pess≤neutral≤opt`、买成交价≤限价/卖≥限价、状态一致性。
4. **覆盖率断言**(⚠️ 关键):上面那些不变量是**必要不充分**的——**一个永远返回 `filled=0` 的实现
   能全部通过**。这不是假设:开发 `SweepAllocator` 时因主动单识别失败,成交从 437 例塌到 74 例,
   **500 例不变量依然报"全过"**。故把覆盖率也**断言死**(有成交≥60%、全成≥30%、穿透≥20%…),
   任一路径被整个封死就直接失败。已实测:把那个 bug 重新注入 → 覆盖率断言当场抓住。
5. **300 例多腿 fuzz**(共享预算的**强不变量**,无需 ground truth)。成交记录带**真实订单号**,
   因此真正走共享预算路径(单腿 fuzz 的成交无订单号 → 永远走退化回退路径,**碰不到这段代码**):
   - **守恒**:同一笔主动单造成的虚拟成交总和 **≤ 它的原始委托量 Q** ← 独立模型必然违反
   - **单调**:每条腿在多腿里的成交 **≤** 它单独跑时的成交(加兄弟腿只会抢走,不会送给你)
   - **位移**:`0 ≤ displaced ≤ Σfilled`
   - 覆盖断言:必须有足够多的腿"被兄弟腿抢占",否则说明共享根本没生效。
   已实测:注入"预算永不绑定"(共享失效)→ 守恒不变量当场报 `Σfilled=6800 > Q=2400`。

## 假设与已知限制

- **无市场冲击**:虚拟单不改变其他人的行为(标准回测假设)。**只要你的单成交了,位移就已经发生**
  ——你"顶替"掉了本会成交的真实单。本模型**不追踪这个位移的后果**(被挤掉的真实单在现实中会改挂、
  会撤单,别的参与者会反应)。这是单订单 L3 回放**不可消除**的近似。
  `displaced` 列就是用来**量化你离这个假设有多远**的:它 = 0 说明零冲击;它很大说明假设已被严重违反。
- **影子记账层读的是真实簿**:被你挤掉成交的真实单,在你的反事实里"本该还挂着",但你去读簿子时
  (簿子按磁带演化)它已经没了。这是"不分叉"的代价 —— 偏差大小由 `displaced` 直接反映。
- **同毫秒多事件排序**影响 `aheadQty` 精度 → 已用乐观/悲观上下界暴露(见上)。
- **t0 在开盘竞价**:开盘 uncross 后转连续时,`aheadQty` 从聚合盘口重置,
  排队退化为聚合近似(后续 cancel 无法再按订单号定位)。t0 在连续段则全程精确。
- **不做的**:让虚拟单**进簿参与撮合**(=撮合引擎)。那样能做到反事实完全自洽,但真实盘口会分叉,
  下游 datacheck / 3秒降频 / 因子链路都会被破坏 —— 明确不做。

## 性能

瓶颈是解析(原占 ~97% 时间)。已做三处优化(结果逐字节不变):
- **匹配前快速拒绝**:只比对 SecurityID 一列,不匹配的行不整行拆分(6位代码走 SSO 不进堆)。~2.5x。
- **分块并行读取**:按字节区间切块、多线程各扫一段,合并顺序无关(build 内部按 seqNo 重排)。
  叠加后单股解析 58s→7s(~8x)。
- **lite build**:`LobBuilder::setLiteMode(true)` 跳过 order/trade 记录表构造
  (getCurrentLob/派生记录/距离比例等只为输出服务的重活),只维护真实簿 + 触发回调。建簿 ~5x。
- `--no-bounds` 再省 2/3 追踪开销(只跑中性)。
- **解析结果缓存**(`--cache-dir`):同日重复跑免重扫大文件。实测 4 只股票:
  冷缓存(解析并写盘)14.8s → 热缓存(直接读定长二进制)0.25s(~60x)。逐字节结果不变。
  缓存带**源指纹 + 解析器版本**校验,源重生成/解析器升级自动失效回源(不会吃过期缓存)。
  `--precache` 可一次性把全市场落盘,之后任意股票查询秒回。
- **多股并行建簿+追踪**(`--workers`):按股票切工作项,`workers` 个线程各算各的、写不相交的结果槽,无锁。

stderr 会打印各阶段(解析 / 建簿+追踪)耗时。
