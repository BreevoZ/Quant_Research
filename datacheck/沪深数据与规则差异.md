# 沪深数据与规则差异（字段层 + 规则层）

> 数据字典 + 市场规则 + 踩坑记录，合并自原 `flow_tl_字段对照.md`。
> 锚点：`datacheck_main.cpp`（解析）、`lob_builder.cpp`（重建）。
>
> 两条主线：
> 1. **数据源**：Flow 是统一格式（沪深通吃）；TL 是 SH / SZ 两套异构 schema → 实际是 Flow / TL-SH / TL-SZ 三种处理。
> 2. **市场**：SZ 是规整的 order-driven 市场，数据干净、字段全；SH 以成交为中心、订单类型少、委托数据有缺口，需重建引擎补。
>
> 规则差异（订单类型、涨跌停、收盘竞价、tick）最终都体现在数据字段与重建处理上。

---

# 一、数据源层（Flow / TL-SH / TL-SZ）

## 1.1 逐笔数据发布机制（根源）

| | 深交所 SZ | 上交所 SH |
|---|---|---|
| 范式 | **order-driven**：逐笔委托 + 逐笔成交两条流 | 历史上**以成交为主**，后期才加逐笔委托 |
| 每笔订单 | **都有显式委托记录** + applSeqNum | 立即成交主动单**只记挂住部分**；有些订单**无委托记录** |
| 撤单位置 | **在成交文件里**（execType=CANCEL） | 在委托流里（Type=D） |
| 序号 | applSeqNum，同 Channel 内**连续无空洞**，可直接排序 | BizIndex，**可能晚于自己的成交**，需重排序 |
| 订单类型字段 | `ordtype` 齐全 | **数据里没有**，只能当限价 |

→ 这是 `lob_builder.cpp` 为 SH 单独做 **重排序 + 派生订单 + 委托量补全** 三招的原因（:231 / :253 / :498）；SZ 干净，不需要。

## 1.2 顶层结构

| | Flow | TL-SH | TL-SZ |
|---|---|---|---|
| 文件组织 | 目录，每秒一个 CSV，沪深 + 全标的混装 | 单个大文件 | 两个文件（委托 + 成交） |
| 读取方式 | 按文件名（=时间）顺序扫 | 字节范围并行分块（顺序无关，靠 BizIndex 重排） | 两文件各自并行，再合并 |
| 市场区分 | 靠 instrumentID 后缀 .SH/.SZ | 单市场（SH） | 单市场（SZ） |
| 解析函数 | `parseFlowDirCombined` (:143) | `parseTLChunk`/`parseTLFileCombined` (:324/:404) | `parseSZOrderChunk`+`parseSZTradeChunk` (:490/:544) |

## 1.3 字段语义对照

| 语义 | Flow | TL-SH | TL-SZ |
|---|---|---|---|
| 证券代码 | `instrumentID`（带 .SH/.SZ） | `SecurityID` | `security`（需 `padSZSecurityID` 补齐） |
| 时间 | `exchangeTime` + `localTime` | `TickTime`（单时戳） | `time`（单时戳） |
| 事件类型 | `actionType` 0/1/2 | `Type` 字符 A/D/T（S 跳过） | 拆两文件：委托文件全挂单；成交文件 `execType` 区分撤/成交 |
| 买卖方向 | `dir` 0=买 1=卖（数字） | `TickBSFlag` 'B'/'S'（字符） | `side` 数字（`SZ_SIDE_BUY`） |
| 订单号 | `bidId`/`askId` | `BuyOrderNO`/`SellOrderNO` | 委托：`applSeqNum`；成交：`bidId`/`offerId` |
| 订单类型 | `priceType` 列直接用 | **无 → 硬编码 '2' 限价** | `ordtype` 码推导（见下） |
| 成交主动方 | `tradeDirection` 列（1/2） | 从成交的 `TickBSFlag` 推（B→1, S→2） | **无 → 默认 0**，靠订单号大小推 |
| 成交额 | `turnover` | `TradeMoney` | 自己算 price×vol |
| 排序键 | `appSeq` | `BizIndex` | `applSeqNum` |

## 1.4 事件类型编码（最易记错）

```
Flow:   actionType  0=委托  1=撤单  2=成交                     (:234-243)
TL-SH:  Type        A=委托  D=撤单  T=成交   (S=状态,跳过)      (:359-368)
TL-SZ:  委托文件 → 全部 actionType=0                           (:529)
        成交文件 → execType: CANCEL→撤单(1)  TRADE→成交(2)      (:601-606)
```

⚠️ **TL-SZ 的撤单藏在「成交文件」里**（execType=CANCEL），不在委托文件。不知道会漏掉全部撤单。

## 1.5 重点坑 / 待确认字段

1. **TL-SH 丢订单类型**：数据无 priceType，硬编码 `'2'` 限价（:382）→「市价单/本方最优单占比」因子在 SH 上失真。
2. **成交主动方可靠性三档**：Flow（显式 tradeDirection）> TL-SH（TickBSFlag 推）> TL-SZ（无，靠订单号大小猜）。做 OFI 方向准确度同序。
3. **订单号空间不同**：Flow 做频道号归一化 `norm(id)=id>1e12 ? id%FLOW_CHAN_MOD : id`（:228）；TL 不做。跨源核对订单要先对齐。
4. **TL-SZ 的 ordtype 是 ASCII 码**：49→'1'(市价)、85→'U'(本方最优)、其它→'2'(限价)（:537）。别误当整数语义。
5. **TL-SZ applSeqNum 可直接排序（已验证）**：同 Channel 内委托+成交合并后是 1..N 连续无空洞（:596-599）。
6. **TL-SH 顺序无关读取**：并行分块后直接 concat，因 `build()` 按 BizIndex 重排 + `resequenceSHOrderBeforeTrade` 保证委托在成交前（lob_builder.cpp:231）。

# 二、市场规则层

## 2.1 订单类型（影响 priceType）

**SZ 连续竞价更丰富**：限价单 + 市价单（对手方最优、本方最优、最优五档即时成交剩余撤销、即时成交剩余撤销、全额成交或撤销）+ **本方最优价单**。

**SH 连续竞价较少**：限价单 + 市价单（最优五档即时成交剩余撤销、最优五档即时成交剩余转限价），历史上**无「本方最优」这种长挂订单**。

→ 对应 SZ `ordtype` 49='1'/85='U'/其它='2'（datacheck_main.cpp:537）；SH 硬编码 '2'。

## 2.2 集合竞价与撤单

| | SZ | SH |
|---|---|---|
| 开盘集合竞价 | 9:15–9:25 | 9:15–9:25 |
| 其中可撤单 | 9:15–9:20 可撤，9:20–9:25 **不可撤** | 同 SZ |
| 收盘集合竞价 | 14:57–15:00（早就有） | 14:57–15:00（2018-08 引入） |
| 收盘竞价撤单 | 不可撤 | 不可撤 |

→ 代码 `CLOSE_AUCTION_START`、"14:57-15:00 收盘集合竞价、交叉单累积进簿"（lob_builder.cpp:24）。

## 2.3 涨跌停 / 价格笼子

| 板块 | 涨跌停 |
|---|---|
| 主板（SH 600/601/603/605，SZ 000/001/002/003） | ±10% |
| 科创板（SH 688） | ±20% |
| 创业板（SZ 300/301） | ±20% |
| ST 股 | ±5% |
| 新股首日 | 不设涨跌幅（竞价阶段有临停） |

**价格笼子**：连续竞价时申报价受保护范围约束（买价不能太高于、卖价不能太低于现价），两市都有。代码里 SZ 市价单的"涨停/地板占位价""价格笼子属于撮合约束、不反写 wt.price"（lob_builder.cpp:488-491）即此。

## 2.4 速查（代码段 / tick / 结算）

| | SZ | SH |
|---|---|---|
| 股票代码 | 000/001/002/003（主板）、300/301（创业） | 600/601/603/605（主板）、688（科创） |
| 基金/ETF | 15xxxx/16xxxx | 5xxxxx（如 501001、510、588） |
| 债券 | 12xxxx | 11xxxx |
| 最小变动 | 股票 0.01，基金/ETF **0.001** | 同 |
| 结算 | 股票 T+1；部分 ETF/债 T+0 | 同 |

⚠️ tick 坑：重建里 `intPrice = price×100` 只到 0.01，**基金/ETF 的 0.001 精度会被截断**（1.542→1.54）。做基金盘口/价差因子要留意。

# 三、对重建与因子的实际影响（把两层串起来）

| 差异 | 后果 |
|---|---|
| SH 委托数据有缺口 | SH 订单级因子（队列、生命周期）比 SZ **可靠性低**；SH 派生单的价是反推值 |
| SH / TL-SH 无 priceType | 「市价单/本方最优占比」因子 **SH 做不了** |
| SZ（datacheck 内）无 tradeDirection | SZ 主动方靠订单号猜，OFI 方向 **SZ 不如 SH/Flow 准** |
| 板块涨跌停不同 | 涨跌停日盘口退化（单边），按板块分别处理临停/封板 |
| 基金 tick 0.001 vs intPrice×100 | 基金盘口价被截断，价差类因子失真 |

---

# 四、一句话总结

- **数据源**：Flow = 统一、自带方向/类型/主动方、id 已归一的成品流；TL = 沪深两套异构 schema，SH 丢订单类型、SZ 撤单藏在成交文件且无主动方标记。
- **市场**：SZ 规整（order-driven + 订单类型丰富 + 字段全），SH 以成交为中心（订单类型少 + 委托有缺口，需补）。
- 规则差异最终都落到字段与重建处理上；下游统一成 `dc::UnifiedRecord`，差异在解析层吸收。
